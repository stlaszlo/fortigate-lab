# Fortinet Training Lab — Deployment and Operations

> Build, rebuild, validate and recover the Azure/Terraform training platform.
>
> This document reflects the validated October 2026 architecture. Where the source material does not establish an implementation detail, it is explicitly marked as TBD rather than assumed.

## 1. Deployment model

The lab is deployed with Terraform into an existing Azure resource group. The code uses reusable modules for:

- network pods;
- FortiGate VMs;
- Linux client/DMZ VMs;
- the Linux transit NVA.

Core topology:

```text
Student Linux VM
  -> Student FortiGate
  -> Student WAN UDR
  -> Transit NVA 10.0.40.4
  -> NVA subnet UDR
  -> Instructor FortiGate 10.0.0.4
  -> Internet
```

The Instructor VNet and each student VNet are peered bidirectionally with forwarded traffic allowed.

## 3. Normal Terraform workflow

Run formatting and validation before changing infrastructure:

```bash
terraform fmt -recursive
terraform validate
terraform plan
```

Review the plan before apply, particularly any FortiGate or NVA replacement.

Apply with:

```bash
terraform apply
```

Do not accept a plan that points student WAN routes or Instructor return routes at the retired NVA address `10.0.0.5`.

The current routing target is:

```text
Transit NVA = 10.0.40.4
```

## 4. Expected Azure route objects

### Student WAN route tables

Each student WAN route table should contain:

```text
0.0.0.0/0 -> VirtualAppliance 10.0.40.4
```

### NVA subnet route table

`rt-fortinet-instructor-nva` should contain:

```text
0.0.0.0/0 -> VirtualAppliance 10.0.0.4
```

### Instructor transit route table

`rt-fortinet-instructor-transit` should contain explicit routes:

```text
10.1.0.0/16 -> VirtualAppliance 10.0.40.4
10.2.0.0/16 -> VirtualAppliance 10.0.40.4
...
10.8.0.0/16 -> VirtualAppliance 10.0.40.4
```

## 5. NVA requirements

The Linux NVA must have forwarding enabled in both Azure and the guest OS.

Guest validation:

```bash
ip addr
ip route
sysctl net.ipv4.ip_forward
```

Expected:

```text
net.ipv4.ip_forward = 1
```

The NVA must keep Azure's normal guest default gateway. Do **not** restore the old guest route override that forced an off-subnet/default gateway directly to `10.0.0.4`.

Azure UDRs are responsible for steering forwarded traffic from `snet-nva` to the Instructor FortiGate.

## 6. Instructor FortiGate requirements

Terraform does not currently manage FortiOS routing/policy state, so FortiGate configuration needs separate validation.

Useful checks:

```text
get system status
get router info routing-table all
show system interface
show router static
show firewall policy
```

The Instructor FortiGate must not retain old static routes pointing student networks at `10.0.0.5`.

Student prefixes should leave via `port1` toward Azure's fabric. Azure's transit-subnet UDR then redirects those student prefixes to `10.0.40.4`.

### Internet policy gotcha

During platform troubleshooting, an Instructor FortiGate policy allowed only `HTTPS` and `PING`. This produced a misleading symptom where ICMP and TCP/443 worked but TCP/80 and arbitrary ports did not.

For baseline platform validation, make sure the Instructor Internet policy permits the traffic required by the current test or exercise. A broad temporary `ALL` service is acceptable during infrastructure validation; tighten it again when the training scenario requires it.

Local traffic generated by the FortiGate itself (for example `execute telnet`) does not prove that forwarded student traffic matches a forward policy.

## 7. Linux VM cloud-init baseline

The Linux VM module uses cloud-init to:

- set the hostname;
- install required packages;
- create the lab MOTD;
- run role-specific commands.

After a VM comes up:

```bash
cloud-init status --wait
cloud-init status --long
```

Known-good result:

```text
status: done
extended_status: done
errors: []
recoverable_errors: {}
```

Client package validation:

```bash
dpkg -l | egrep 'curl|dnsutils|hping3|iperf3|jq|nmap|tcpdump|traceroute'
```

## 8. Rebuilding all student client and DMZ VMs

The client and DMZ VMs are disposable. To force a cohort-wide Linux rebuild using the Terraform state addresses:

```bash
terraform apply $(
  terraform state list \
    | grep 'azurerm_linux_virtual_machine' \
    | grep -Ei '(client|dmz)' \
    | sed 's|^|-replace=|'
)
```

Before executing, preview the selected resources:

```bash
terraform state list \
  | grep 'azurerm_linux_virtual_machine' \
  | grep -Ei '(client|dmz)'
```

A future quality-of-life improvement is a `vm_generation` input included in client/DMZ `custom_data`; bumping it would intentionally trigger a cohort rebuild without assembling `-replace` flags. This is a proposed improvement, not part of the current validated Terraform source.

## 9. Post-deployment validation

Start with `student01` and validate the complete chain before spot-checking another pod.

### Linux client

```bash
cloud-init status --wait
ping -c 3 8.8.8.8
curl -I http://archive.ubuntu.com
curl -I https://archive.ubuntu.com
dig google.com
sudo traceroute 8.8.8.8 -T -p 443
```

Known-good traceroute beginning:

```text
1  10.1.10.4
2  10.0.40.4
3  10.0.0.4
```

Azure may not expose useful TTL-expired hops after the Instructor FortiGate; this is not itself a failure if end-to-end connectivity works.

### Instructor FortiGate capture

Example:

```text
diagnose sniffer packet port1 'host 10.1.0.4' 4 0 l
```

Confirm generated student traffic appears and that the corresponding Forward Traffic logs show the expected policy/action.

### NVA capture

Example:

```bash
sudo tcpdump -ni any host 10.1.0.4
```

### Azure Network Watcher

For a healthy `student01` Internet path, Network Watcher should show the sequence:

```text
10.1.10.10 -> 10.1.10.4 -> 10.0.40.4 -> 10.0.0.4 -> Internet
```

## 10. Effective-route checks

When routing looks wrong, check the Azure effective routes on the relevant NIC rather than inferring behavior from Terraform alone.

Examples:

```bash
az network nic show-effective-route-table \
  --resource-group rg-fortinet-cohort-121026 \
  --name fg-instructor-01-nic-port1
```

Check the student FortiGate WAN NIC and NVA NIC using their actual NIC names as well.

Expected high-level behavior:

- Student FG WAN: `0.0.0.0/0 -> 10.0.40.4`
- NVA: `0.0.0.0/0 -> 10.0.0.4` via subnet UDR
- Instructor FG port1: each student `/16 -> 10.0.40.4`

## 11. Troubleshooting order

Use one flow and trace it hop by hop. Avoid changing multiple routing/security components at once.

1. Confirm client source/destination and local route.
2. Sniff Student FortiGate ingress and egress.
3. Confirm Student FG policy, SNAT and session state.
4. Sniff the NVA.
5. Sniff Instructor FortiGate `port1`.
6. Check Instructor forward policy and NAT.
7. Only then move outward to Azure effective routes, NSGs or destination-specific behavior.

Useful FortiGate commands:

```text
diagnose sniffer packet any '<filter>' 4 0 l
diagnose debug flow filter clear
diagnose debug flow filter addr <ip>
diagnose debug flow trace start 100
diagnose debug enable
diagnose sys session list
```

Remember: a UDR is L3 routing. If the same path consistently allows TCP/443 but blocks TCP/80 or TCP/8443, inspect L4 policy/security controls before assuming the route itself is protocol-selective.

## 12. Known historical failure modes

### Shared-subnet NVA loop

The original NVA lived on `snet-transit` with the Instructor FortiGate. UDR experiments produced a routing loop and Network Watcher reported `UDRLoop`.

Resolution: move the NVA to the dedicated `10.0.40.0/24` subnet and use independent subnet route tables.

### Instructor policy only allowed HTTPS and PING

Symptoms:

- ICMP worked;
- HTTPS worked;
- HTTP and other TCP ports failed;
- locally-originated Instructor FG tests could still succeed.

Resolution: correct the Instructor FortiGate forward policy service set.

### Broken cloud-init YAML

An earlier generated `packages:` block had invalid indentation, causing YAML parsing failure before package installation.

Resolution: fix Terraform template indentation and redeploy the Linux VMs.

### APT appeared to implicate Azure Ubuntu mirrors

`archive.ubuntu.com:443` worked while APT initially stalled against `azure.archive.ubuntu.com`. The decisive issue was the Instructor FortiGate's service restriction, not an Azure-specific Ubuntu route.

## 13. Recovery strategy

The Linux VMs are intentionally disposable and can be replaced through Terraform.

For FortiGates, maintain known-good configuration exports outside the appliances. At minimum keep:

```text
instructor-baseline.conf
student-baseline.conf
```

The current source material does not define an automated FortiOS backup/restore pipeline. Until one exists, baseline exports should be treated as an operational prerequisite before students begin configuration-changing labs.

## 14. Release checkpoint

The current platform state is suitable for a repository milestone such as:

```text
student-pods-ready
```

Recommended release criteria:

- Terraform plan is clean/expected;
- student client and DMZ cloud-init complete;
- student Internet path validates through FG -> NVA -> Instructor FG;
- Instructor FG logging is visible;
- baseline FortiGate configurations are exported;
- one student pod completes the first training lab from a clean state.
